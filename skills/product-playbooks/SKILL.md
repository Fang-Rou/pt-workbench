# 产品攻击手册（product-playbooks）

> 这一层沉淀的是**按产品组织、经过实战验证的攻击方法论**。
> 与其他层的分工：
> - `state/vuln_knowledge.json` = 漏洞实例 + 平台处置（防重复提交）
> - `skills/<漏洞类别>/` = 通用技术知识（理论向）
> - `skills/product-playbooks/` = 某个产品怎么打（实战验证过的链）← 本层
> - `scripts/` + `pocs/` = 自动化资产
> - `state/WORKFLOW.md` = 流程纪律

## Playbook 固定结构

每个产品手册必须包含以下 9 节（没有内容就写"暂无"，不许省略）：

1. **状态与适用范围**：验证状态（已验证/部分验证/理论）、已验证目标数、最后验证日期、平台处置现状
2. **指纹识别**：怎么确认目标是这个产品、怎么定版本、二开常见去特征手段
3. **已验证攻击链**（核心资产，一条链一小节）：前提条件 → 完整步骤（指纹→验证→提数据→证据）→ 复用资产（脚本路径）→ 证据模板 → 提交参数 → 迁移条件（换目标要重新验证什么）
4. **踩坑库**：该产品专属的坑（WAF 通道、编码陷阱、组件行为）
5. **失效条件**：什么情况下链不成立（版本修复、配置变更）
6. **未验证方向**：值得试但还没试的 backlog
7. **盲区声明**：本手册**不覆盖**什么——读手册获得速度的同时必须知道盲区在哪，这是发散探索的邀请函，不是免责声明
8. **案例索引**：每次实战一行，只写 delta
9. **资产清单**：脚本/POC/交付样板的路径

## 沉淀规则（什么时候必须写）

1. **被验证有效的瞬间**：平台确认利用成功、拿到真实数据、真实状态改变 —— 立刻在案例索引加一行，新技巧升格进攻击链小节。驳回但理由是"已有人提交" = 链完全有效，照常沉淀。
2. **踩坑瞬间**：新坑当次写进踩坑库，不等复盘。
3. **负结果**：链在新版本/新配置失效 → 写进失效条件，防止下次浪费半天。
4. **checkpoint 纪律**：每次 milestone checkpoint 必须能回答"这次什么 delta 进了哪个 playbook"；答不出来说明这次没学到可复用的东西，或者忘了沉淀。

## 复利规则（怎么越弄越强）

- **delta 而非叙事**：案例索引只写"这次比手册多了什么/修正了什么"。完整故事属于交付文件夹，不属于手册。叙事不产生复利，delta 才产生。
- **升格**：同一技巧在两个产品手册里各出现一次 → 第三次出现前把它升格成通用规则，写进对应漏洞类别 skill 或 WORKFLOW。升格是防膨胀机制：通用知识不住在产品手册里，手册只留产品特有内容。
- **蒸馏**：每积累 10 个案例或每季度，通读全部手册做一次蒸馏：合并重复、淘汰失效、确认资产路径仍有效、把老案例行归档进手册尾部 `## 案例归档`。
- **阅读先于动手**：指纹命中产品家族时，先读手册再动手；手册没有的方向才从零探索，探索结论回流手册。

## 反僵化规则（手册是起点，不是边界）

沉淀系统最大的两个死法：文件膨胀到拉不动；模式锚定到只会打手册里有的洞。规则：

1. **80/20 探索预算**：每次实战先用已验证链把已知面快速打完（这部分应当便宜、快），然后**强制预留约 20% 精力**探索手册未覆盖的攻击面。跑完手册就收工是不合格的实战。
2. **盲区即邀请**：手册第 7 节盲区声明是探索清单。每次实战至少考虑过盲区清单上的每一项（哪怕结论是"这次不适用"）。
3. **backlog 双向流动**：第 6 节未验证方向必须既被消耗（试过的移入攻击链/踩坑/失效条件）又被补充（新想法进 backlog）。只增不减或只减不增都说明这条线在僵化。
4. **负结果是资产**：探索失败（某方向确实没洞）写入盲区或失效条件，下次不用重付学费——这也是发散的积累，不是浪费。
5. **发散的燃料在手册之外**：新 CVE 情报、新平台反馈、新项目线（换目标类型/行业）才是新模式的来源；手册只负责让已知部分变便宜，省出注意力给它们。

## 使用时机

- 侦察阶段指纹命中索引中任意家族 → 先读对应手册
- 实战结束（无论成败）→ 按沉淀规则回写
- 新会话恢复断点后，若 next_action 涉及已知家族 → 读手册代替读旧对话
